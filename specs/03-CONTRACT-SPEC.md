The **`03-CONTRACT-SPEC.md`** specification serves as the high-level, unambiguous **single source of truth** for the system. Its objective is not to detail implementation logic, but to define boundaries, data types, and integrity guarantees across all components: the web client, backend API, database, and asynchronous messaging.

At a high level and without code syntax, this document is structured around three core pillars:

---

### 1. Data Model & Persistence Rules (PostgreSQL)

Defines how data is structured and protected within the relational database:

* **Entities and Relationships:**
* *Tenants:* The root organizational entity representing the fund or institution.
* *Accounts (Wallets):* An entity bound to a tenant holding the balance and accounting currency.
* *Transactions:* An immutable ledger record of fund movements associated with an account.


* **Monetary Precision Guarantee:** Strictly prohibits imprecise floating-point types, enforcing fixed-point decimals or integer cents to eliminate financial rounding discrepancies.
* **Database-Level Idempotency Constraint:** Enforces a composite unique constraint across the tenant identifier and the client-supplied idempotency key. If two identical requests arrive concurrently, the database engine physically aborts the second attempt, preventing duplicate operations.


* **Multi-Tenant Isolation Rule (Row-Level Security):** Mandates that no business data row can be read or modified unless it matches the tenant identifier assigned to the active database session.



---

### 2. Interface Contracts & Validation (API & TypeScript)

Defines the exact expectations at the HTTP boundary before any data reaches internal application logic:

* **Mandatory Security and Context Headers:**
* *Tenant Identifier:* Establishes the organizational scope of the session.


* *Idempotency Key:* A unique alphanumeric token generated by the frontend to unambiguously represent user intent.


* *Correlation Identifier:* A tracking token passed along the request pipeline to enable distributed tracing and log debugging.




* **Input Payload Semantic Validation:**
* *Financial Limits:* The deposit amount must be strictly positive and capped below an operational ceiling.
* *Banking Formats:* Structural validation of source bank account details (such as account holder and IBAN).


* **Standardized Responses:**
* *Success Response:* Returns the transaction ID, initial lifecycle state (`PENDING`), and an explicit boolean flag indicating whether the transaction was freshly created or resolved as an idempotent duplicate.
* *Error Response:* A predictable structure containing an error code, a human-readable message, and the correlation identifier for support and debugging.



---

### 3. Asynchronous Messaging Contract (Event Envelope)

Defines the structure of messages published to an event broker (such as Amazon SQS or EventBridge) to decouple background execution:

* **Governance Metadata (Envelope):** Global event ID, schema version (to allow backward-compatible evolution), UTC timestamp, tenant ID, and the correlation ID inherited from the originating HTTP request.


* **Business Payload:** The essential dataset needed by background workers to perform external settlement: internal transaction ID, target account ID, reconciliation amount, and source banking details.
