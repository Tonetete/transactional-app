# infra: Terraform

Replaces `apps/infra` (AWS CDK), which stays until the migration is complete (`odd/tasks/terraform-migration.md`).

```
infra/
  modules/   network, messaging, database, compute, provisioning   (settlement, web_hosting follow)
  envs/
    aws/     real AWS: remote S3 state, data protected
    floci/   local emulator: endpoint on every service, disposable data
```

A module describes one concern and exposes only what its consumers need. The CDK `local` flag is replaced by explicit
inputs: `protect_data` (deletion protection, final snapshot, secret recovery window), `enable_http_listener`,
`enable_dev_login`, `aws_endpoint_override` and `secret_recovery_window_days`. `envs/aws` leaves them at their safe defaults.

## Floci
```bash
cd infra/envs/floci
terraform init
terraform apply -var image=<ecr image> -var certificate_arn=<acm arn>   # names are acex-floci-*, coexisting with the CDK stack
# the certificate comes from scripts/floci-cert.sh; image build+push moves into the deploy script in a later slice
terraform destroy
```
Resource names include `<project>-<environment>`; the CDK stack uses different names, so both can live in one floci.
Verified on floci 2.3.0: apply with network/messaging/database only (38 resources, ~1.5 min); with compute and provisioning also wired, apply (83 resources, ~1.5 min), an empty second plan (`terraform plan -detailed-exitcode` exits 0), ECS services `api`/`relay` reaching their desired RUNNING counts, and a clean destroy (~2.5 min, no leftover secrets or queues).

## Tests
`terraform test` runs against mocked providers (no floci needed), one file per module:
```bash
for m in infra/modules/*; do (cd $m && terraform init -backend=false >/dev/null && terraform test); done
```

## Notes
- Database passwords are generated by Terraform, so they are in the state. The AWS state bucket must be private,
  encrypted and versioned.
- floci reports security-group references as `000000000000/sg-...`, which makes Terraform plan a permanent in-place change
  on rules that reference another security group. The `compute` and `provisioning` modules set
  `lifecycle { ignore_changes = [referenced_security_group_id] }` on every rule that references another security group,
  so this drift never shows up in `terraform plan`; real AWS reports the ARN it was given and is unaffected.
